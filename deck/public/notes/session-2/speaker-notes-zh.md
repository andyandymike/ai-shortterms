## 06 · C7｜How Computer Use is trained

[打开本页](/session-2#computer-use/C7)

> 画面 1 / 3 · 误点 Cancel 后表单关闭；退货未创建，反馈为失败

模型点了 Cancel，表单被关掉，退货没有创建。中间把这个结果记为失败。训练反馈要看任务有没有完成，不能只看有没有点击。

> 画面 2 / 3 · 训练得到新模型

把这样的练习积累起来，训练程序根据反馈反复调整 weights，也就是模型内部学到的参数。OpenAI 的 Computer Use 模型就使用了强化学习，英文是 reinforcement learning。这里把多轮练习和更新缩成一段示意。

> 画面 3 / 3 · 截图变了，weights 保持不变

现在是 inference，也就是使用训练好的模型。按钮换了位置，新截图改变 context；中间的 weights 保持固定，模型仍能重新找按钮。刚才的弹窗恢复也属于这个阶段。

## 09 · J1｜How to ask Jev a question

[打开本页](/session-2#jev/J1)

> 画面 1 / 2 · 一题对应一个答案；三个部门是我们给的选项

这封退货邮件就是本次输入，这里叫 state。我们定义问题“交给哪个部门”，再提供退货、账单、物流三个选项。这种题型叫 Choice。Jev 给每个选项一个概率；选项由我们定，判断由模型做。

> 画面 2 / 2 · 两题、两个答案；Choice、Score、Noul 是可选题型

再加一道题：“客户想退货吗？”Noul 返回“是”的概率。现在两题对应两个答案。下面的 Choice、Score、Noul 是三种题型，Score 用来自定标准打分；它们不是固定三个输出。问题和数量可以随请求改变，不用为每道新题重新训练。

## 11 · J3｜How Jev differs from an LLM

[打开本页](/session-2#jev/J3)

> 画面 1 / 2 · 一次请求的 JSON 包含两题的答案

回到刚才那封邮件和两道题。左边的 LLM 一次请求就能回答，用 JSON Schema 限定字段和类型。它仍然通过 decoding 顺序生成这份 JSON。画面为了好读，把输出分成了较大的文字片段。

> 画面 2 / 2 · 两个独立答案由 API 装进 JSON

按 TypeSafe 的说明，右边的 Jev 根据同一份 state，并行给出各题的概率，再由 API 包装成 JSON。它省去了把答案逐段写成文字的顺序输出，所以可能降低延迟；具体快多少仍要实测。两边拿到的都是 JSON，产生答案的过程不同。

## 12 · J5｜How Jev is trained

[打开本页](/session-2#jev/J5)

> 画面 1 / 3 · 预测退货 95%，已知答案是账单

这次换成重复扣款的邮件，客户还说要留下鞋子。已知应该交给账单部门，示意模型却给“退货”95% 的概率。训练要纠正两件事：判断错了，而且错得很有把握。

> 画面 2 / 3 · 同一封邮件的判断变为 billing

和上一章一样，许多练习的反馈用来调整 weights。TypeSafe 把这类继续训练称为 RLCD，目标是判断更准、概率更可信。再看同一封邮件，模型已偏向账单；是否学会，还要换新题检查。

> 画面 3 / 3 · 80% 的含义：长期接近八成正确

上面是没参与训练的新邮件，weights 固定，模型给账单 80% 的概率。Calibration，校准，要看许多类似预测：说八成把握时，长期是否约八成正确。下面的十格只解释这个含义，不能用这一封邮件证明校准。

## 13 · J8｜When to use Jev

[打开本页](/session-2#jev/J8)

> 画面 1 / 3 · returns 0.94，代码把工单送到退货队列

这里每来一封工单，都要判断交给哪个部门。Jev 对这封退货邮件给出 returns 0.94，代码按示例规则：最高概率至少 0.90，就自动分流。Jev 给出判断，真正移动工单的是代码；0.90 是我们设置的演示门槛。

> 画面 2 / 3 · 退货与扣款两个问题，工单转人工确认

换一封邮件，客户既要退货，又说被重复扣款。现在 returns 是 0.61，billing 是 0.35。只拿最高的 returns 就直接分流，可能漏掉另一件事。按刚才的规则，代码把它交给人工确认。概率帮助我们决定何时自动处理、何时先检查；前提是用真实工单验证过这些概率是否可信。

> 画面 3 / 3 · 高频小判断值得比较 Jev；偶发分类或完整回复可保留 LLM

当同一种小判断反复出现、答案范围清楚，而且延迟或调用成本开始影响流程时，就值得试 Jev。比如工单分类、优先级评分。若只是偶尔分类，或主要任务是写完整回复，现有 LLM 返回 JSON 或文字可能已经够用。也可以让 Jev 给判断、代码分流、LLM 写回复。最终拿同一批新工单，先比错误和 calibration，再比延迟和成本。

## 15 · R4｜How an improvement loop works

[打开本页](/session-2#rsi/R4)

> 画面 1 / 3 · A 排对了，右侧仍使用 A

A 是原来使用的排序程序，结果正确。现在想让它少做些工作。这里把比较和写入次数加起来当作工作量，不是运行秒数。三个候选是预先写好的，数字移动来自实际执行。

> 画面 2 / 3 · B 的结果有误，继续使用 A

第一次尝试 B，只走一遍，工作确实少了，但红色数字还没排对。改得快没有用，先得正确，所以右边 IN USE 仍然是 A。

> 画面 3 / 3 · C 通过六项测试，以更少工作替换 A

再试 C。它通过同一组六项测试，工作量也更少，才替换 A。这就是提出改法、测试、保留结果。眼下变好的是排序程序；如果改的是 AI 自己的工具、参数，或者训练程序，才开始接近我们今天要讲的几条路线。

**转场｜** 第一种做法：模型不变，改它做事的方法。

## 16 · R8｜How an agent improves its workflow

[打开本页](/session-2#rsi/R8)

> 画面 1 / 2 · 工作流新增 Validate the patch，失败补丁修正后成功应用

第一条路线改 Agent 的代码。Agent 可以理解成模型加上工具和做事流程。左边 LLM 的 weights 没变，变的是中间：编辑代码后先检查补丁能不能应用，有错就返回重试。DGM，也就是 Darwin Gödel Machine，报告过这类自改工具的做法；这里把过程画成一个简单例子。

> 画面 2 / 2 · 在别的编程任务上评估版本，版本库中的 v2 参与后续修改

一个补丁成功还不够，要用别的编程任务评估整个 Agent。DGM 会保留一个版本库，从不同版本继续探索；图里只画了一条分支。关键是，改好的 Agent 也会参与后面的自我修改。底层模型没重训，系统的做事能力仍然可能改善。

## 17 · R9｜How a model learns from its own solutions

[打开本页](/session-2#rsi/R9)

> 画面 1 / 2 · 正确答案被筛出；错误的 7 根据答案提示重试为 10

第二条路线像做题后整理练习材料。STaR 从已有题目和标准答案开始，让模型写解题过程。第一题答对，留下；第二题答成 7，给它答案 10，再试着写出能得到 10 的过程。它生成的是解题过程，题目和判断答案的依据仍由外部提供。

> 画面 2 / 2 · 训练改变 weights，得到的模型继续生成下一批解题过程

积累很多这样的例子，再做 fine-tuning，微调：用选出的题目和解题过程训练模型，改变 weights。训练后的模型再生成下一批，继续筛选和训练。这比在一次聊天的 context 里记住一句提示多了一步。也要注意，答案碰巧正确不保证过程正确，模型有没有学好还得用新题检查。

**转场｜** 第三条路线不改做题方式，而是改训练所用的计算程序。

## 18 · R5｜How AlphaEvolve improves AI training

[打开本页](/session-2#rsi/R5)

> 画面 1 / 2 · Gemini 提议的 kernel 改动通过正确性与速度检查

训练 AI 时，有些小段计算会反复运行，这叫 kernel。可以把一次大计算分成小块，怎样分才更适合硬件，会影响效率。AlphaEvolve 用 Gemini 提出改法，再实际运行，检查答案是否正确、速度是否改善。和排序页一样，不能只听 AI 说它更好。

> 画面 2 / 2 · 同一块 K 移入 Gemini 训练，显示已报告的效率收益

现在改好的 K 回到 Gemini 的训练里。DeepMind 报告，这类 kernel 平均加速 23%，整体训练时间约减少 1%。因为它反复运行，局部节省也有价值。但这里证明的是训练更省；是否因此得到更会研发的 AI，还要另外检验。

## 19 · R6｜When does improvement become recursive?

[打开本页](/session-2#rsi/R6)

> 画面 1 / 2 · 三列分别是 Agent 代码、模型 weights、训练工具

把三种做法并排看：DGM 改工具和流程，STaR 通过训练改 weights，AlphaEvolve 改训练用的程序。这是帮助理解的分法，不是 RSI 只有这三种。它们的共同问题是：改进会不会反馈到下一轮，帮助系统做出后续改进？

> 画面 2 / 2 · 条件性回路：v2 回到左侧做改进，右侧出现 v3 问号

递归发生在这条回来的箭头：上一轮改好的系统，参与下一轮改进。这里的系统既可以是模型，也可以包含工具和流程。要检验它是否真的更会改进，得用新任务和相同预算比较。DGM 展示了有限编程 Agent 的反馈回路；这些例子都不能直接推出 AI 已经能无限自我升级。
