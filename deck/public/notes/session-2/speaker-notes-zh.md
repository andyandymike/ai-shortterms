## 04 · C4｜How Computer Use works

[打开本页](/session-2#computer-use/C4)

> 画面 1 / 3 · 定位输入框

右边是 context，也就是模型当前能用的信息：目标、截图和操作记录。左边已经标出了订单号输入框。把“要找什么”对应到屏幕位置，叫 UI grounding。

> 画面 2 / 3 · 完整表单

表单已经填好。模型通过 tool call 请求工具输入订单号、选择原因；工具执行后，新截图回到 context。现在确认的是表单填对了，还没有创建退货。

> 画面 3 / 3 · 新截图确认退货已创建

提交后，应用生成了 R-204 回执，新截图也把它带了回来。这才确认目标完成。Agent 就是这样把观察、判断、操作和结果检查接成循环。

## 05 · C5｜How Computer Use recovers

[打开本页](/session-2#computer-use/C5)

> 画面 1 / 3 · 旧位置点击失败

这次表单被弹窗挡住了，右边却还是旧截图。工具按旧位置点了下去，但退货没有创建。点击成功执行，和任务成功完成，是两件事。

> 画面 2 / 3 · 新截图看见弹窗，定位关闭按钮

新截图已经把弹窗带进 context，关闭按钮也重新定位好了。模型现在知道障碍在哪里，下一步才有依据。

> 画面 3 / 3 · 新截图确认完成

关掉弹窗、检查表单、重新提交，最后拿到回执。这次恢复靠的是更新观察，再调整动作；并没有现场重新训练模型。

## 06 · C7｜How Computer Use is trained

[打开本页](/session-2#computer-use/C7)

> 画面 1 / 3 · 点击没有完成退货；任务结果成为训练反馈

先看一次练习：点击执行了，却没有创建退货。训练反馈要看任务有没有完成，不能只看有没有点击。

> 画面 2 / 3 · 训练得到新模型

把这样的练习积累起来，训练程序根据反馈反复调整 weights，也就是模型内部学到的参数。OpenAI 的 Computer Use 模型就使用了强化学习，英文是 reinforcement learning。这里把多轮练习和更新缩成一段示意。

> 画面 3 / 3 · 截图变了，weights 保持不变

现在是 inference，也就是使用训练好的模型。按钮换了位置，新截图改变 context；中间的 weights 保持固定，模型仍能重新找按钮。刚才的弹窗恢复也属于这个阶段。

## 09 · J1｜How to ask Jev a question

[打开本页](/session-2#jev/J1)

> 画面 1 / 2 · 一题对应一个答案；三个部门是我们给的选项

这封退货邮件就是本次输入，这里叫 state。我们定义问题“交给哪个部门”，再提供退货、账单、物流三个选项。这种题型叫 Choice。Jev 给每个选项一个概率；选项由我们定，判断由模型做。

> 画面 2 / 2 · 两题、两个答案；Choice、Score、Noul 是可选题型

再加一道题：“客户想退货吗？”Noul 返回“是”的概率。现在两题对应两个答案。下面的 Choice、Score、Noul 是三种题型，Score 用来自定标准打分；它们不是固定三个输出。问题和数量可以随请求改变，不用为每道新题重新训练。

## 10 · J2｜How decoding works

[打开本页](/session-2#jev/J2)

> 画面 1 / 1 · We 已加入 context，下一轮候选已出现

普通 LLM 写文字时，会逐步选出下一个 token，这个过程叫 decoding。Token 是词、字符或文字片段。这里已经选出 We，并把它加进左边的 context；右边接着预测 can 还是 will。新生成的内容参与下一步判断，重复这个过程就能写出一句话。

## 11 · J3｜How Jev differs from an LLM

[打开本页](/session-2#jev/J3)

> 画面 1 / 2 · 一次请求的 JSON 包含两题的答案

回到刚才那封邮件和两道题。左边的 LLM 一次请求就能回答，用 JSON Schema 限定字段和类型。它仍然通过 decoding 顺序生成这份 JSON。画面为了好读，把输出分成了较大的文字片段。

> 画面 2 / 2 · 两个独立答案由 API 装进 JSON

按 TypeSafe 的说明，右边的 Jev 根据同一份 state，并行给出各题的概率，再由 API 包装成 JSON。它省去了把答案逐段写成文字的顺序输出，所以可能降低延迟；具体快多少仍要实测。两边拿到的都是 JSON，产生答案的过程不同。

## 12 · J5｜How Jev is trained

[打开本页](/session-2#jev/J5)

> 画面 1 / 3 · 预测退货 95%，已知答案是账单

这次换成重复扣款的邮件，客户还说要留下鞋子。已知应该交给账单部门，示意模型却给“退货”95% 的概率。训练要纠正两件事：判断错了，而且错得很有把握。

> 画面 2 / 3 · 同一封邮件的判断变为 billing

和上一章一样，许多练习的反馈用来调整 weights。TypeSafe 把这类继续训练称为 RLCD，目标是判断更准、概率更可信。再看同一封邮件，模型已偏向账单；是否学会，还要换新题检查。

> 画面 3 / 3 · 80% 的含义：长期接近八成正确

上面是没参与训练的新邮件，weights 固定，模型给账单 80% 的概率。Calibration，校准，要看许多类似预测：说八成把握时，长期是否约八成正确。下面的十格只解释这个含义，不能用这一封邮件证明校准。

## 15 · R4｜How an improvement loop works

[打开本页](/session-2#rsi/R4)

> 画面 1 / 3 · A 能做对，先保留 A

A 是原来使用的排序程序，它能排对。下面记录比较和写入的次数，把它们相加作为本例的工作量。我们想找一个同样做对、工作量更少的办法。A、B、C 是预写的程序，动画来自它们的实际运行。

> 画面 2 / 3 · B 顺序不对，继续使用 A

第一次尝试 B，只排一遍。操作确实少了，但红色数字的顺序还不对，所以拒绝 B。右边 IN USE 仍然是 A。

> 画面 3 / 3 · C 通过同一组测试，且操作更少；A 被 C 替换

B 失败后再试 C。C 通过同样的六项检查，总工作量也更少，才替换 A。这个循环改进了排序程序，还没有改进做研发的 AI，所以本身不等于 RSI。

## 16 · R5｜How AlphaEvolve improves AI training

[打开本页](/session-2#rsi/R5)

> 画面 1 / 2 · Gemini 提出的 kernel 改法通过检查

把排序程序换成训练 AI 用的 kernel，也就是反复执行的小段计算程序，比如矩阵乘法。AlphaEvolve 用 Gemini 提出改法，再由评估器检查结果和速度。现在 K 已经通过检查。

> 画面 2 / 2 · 改好的 K 进入 Gemini 训练；提效数字出现

同一块 K 已经进入 Gemini 的训练流程。DeepMind 报告，这个 kernel 提速 23%，整体训练时间减少约 1%。它和 RSI 的联系在于：AI 改好的工具，又用来训练 AI。但目前证明的是训练提效，还不是更会研发的新 AI。

## 17 · R6｜How improvement becomes recursive

[打开本页](/session-2#rsi/R6)

> 画面 1 / 3 · v2 出现，但是否更会做研发仍未知

从这里开始是假设。假如把省下的算力用于更多训练，帮助开发出了右边的 v2，它也不一定比 v1 更会做研发，所以还带着问号。

> 画面 2 / 3 · v1 和 v2：新任务，相同预算

给 v1 和 v2 新的 kernel 优化任务，用相同的尝试预算，比较谁能找到正确、有用的改法。这是在检验下一轮的改进能力，图里还没有胜负。

> 画面 3 / 3 · v2 接替 v1，提出下一项改进；右侧出现 v3？

假设 v2 通过检验，确实更擅长这项工作，它就接过左边 v1 的位置，继续帮助开发 v3。v3 还要重新检验。上一轮得到的新 AI，成为下一轮的改进者，这一步才让改进递归下去。
